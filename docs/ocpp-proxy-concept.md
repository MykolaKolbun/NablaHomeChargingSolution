# Концепція: прозорий OCPP-проксі

Статус: **ідея** (2026-11-05). Окремий майбутній проєкт — не частина Nabla Home і не частина комерційного OCPP.
Код, якщо знадобиться, копіюється (з EVOCPP тощо), спільних залежностей немає.

## Навіщо

Станцією керує чужа закрита система (CSMS) — наприклад, паркінг Skidata. Вона робить свою частину добре, але
не вміє того, що потрібно клієнтам, а її розробники змін не вносять. Замінити її не можна.

Проксі стає між станцією та CSMS:

```
Зарядна станція ──wss──► Проксі ──wss──► CSMS паркінгу (Skidata)
                           │
                           └──► Наш сервіс (передплата, ліміти, діагностика)
```

Принцип: **CSMS паркінгу бачить станцію такою, як є, і отримує відповіді на свої запити** — для неї нічого
не змінюється. Проксі лише **читає весь потік у реальному часі** і **додатково** надсилає станції кілька
своїх команд. Решта керування — окремо, у нашому сервісі.

## Попередній сценарій (від якого відмовились)

Паркінг Skidata, зарядні станції під його керуванням. Біля станцій — окремий зчитувач паркувальних квитків
(один на 10+ станцій). Клієнт підключає авто, сканує квиток, обирає станцію — заряд починається.
Паркінг працює лише з **післяплатою** (заряд + паркування одним чеком). Клієнтам потрібна була **передплата
окремим платежем**.

Як зробили:
1. У нашому додатку клієнт сплачує заряд і отримує **окремий квиток лише для заряджання**; сканує його на
   зчитувачі замість паркувального. Ця частина працювала добре для всіх.
2. Обмеження сплаченим обсягом: MeterValues читали **з таблиці в базі даних паркінгу**, куди їх записує Skidata.
3. Коли сплачене вичерпано — `RemoteStop` **через окремий командний інтерфейс** паркінгу.

Проблеми:

| Проблема | Причина |
|---|---|
| Дані із запізненням | Читали не потік від станції, а те, що (і коли) Skidata записав у свою БД |
| Обрив сесії не оновлювався вчасно | Стан сесії видно лише після запису паркінгом |
| Завершення вручну (від'єднали кабель) — дані «підвисали» | Те саме: StopTransaction доходив до нас через БД паркінгу |
| Немає зворотного зв'язку на зупинку | Командний інтерфейс не повертав відповідь станції на `RemoteStop` |
| Складно визначити, на якій станції клієнт почав заряд | Один зчитувач обслуговує 10+ станцій; зв'язок «квиток → станція» треба було відновлювати з БД |

## Той самий сценарій через проксі

1. Клієнт сплачує в додатку, отримує квиток для заряджання (як раніше). Наш сервіс знає: квиток → оплачено N кВт·год.
2. Клієнт сканує квиток, паркінг запускає заряд як завжди (сам вирішує, сам надсилає `RemoteStart` / приймає
   `Authorize` — проксі це лише пропускає).
3. Станція надсилає `StartTransaction` — **через проксі**. Проксі бачить одразу: яка станція (з'єднання),
   `connectorId`, `idTag` (= номер квитка — **перевірити**, що саме паркінг передає в idTag), `meterStart`, а з
   відповіді паркінгу — `transactionId`. Питання «на якій станції почав» зникає.
4. MeterValues проходять через проксі — наш сервіс рахує енергію **в момент надходження**, без затримки БД.
   Ближче до ліміту — `TriggerMessage(MeterValues)` для свіжого показу (не змінюючи `MeterValueSampleInterval`,
   який належить паркінгу).
5. Сплачене вичерпано → проксі сам надсилає станції `RemoteStopTransaction(transactionId)` і **сам отримує
   відповідь** (`Accepted` / `Rejected`) — зворотний зв'язок є. Паркінг цю команду й відповідь не бачить.
6. Станція надсилає `StopTransaction` — проксі передає паркінгу (для нього це звичайне завершення, він закриває
   сесію і рахує своє), а наш сервіс бачить точну енергію й `reason` одразу.
7. Від'єднання кабелю, обрив, PowerLoss — так само видно миттєво: `StatusNotification` / `StopTransaction` /
   зникнення WebSocket.

| Стара проблема | Через проксі |
|---|---|
| Запізнення даних | Потік від станції в реальному часі |
| Обрив / завершення вручну | `StopTransaction`, статуси й розрив з'єднання видно одразу |
| Немає відповіді на зупинку | Відповідь станції на наш `RemoteStop` приходить у проксі |
| Яка станція | З'єднання + `connectorId` + `idTag` у `StartTransaction` |
| Залежність від БД і командного інтерфейсу паркінгу | Не потрібні |

## Правила проксі

- **За замовчуванням — прозорий.** Усі повідомлення в обидва боки пересилаються без змін, у тому ж порядку.
- **Свої команди — лише з білого списку:** `RemoteStopTransaction`, `TriggerMessage`, `GetConfiguration`;
  `ChangeConfiguration` — лише окремо узгоджені ключі (напр. запобіжники з [CB-009](commercial-backlog.md)).
  Нічого, що змінює стан, яким керує паркінг (профілі потужності, `MeterValueSampleInterval`, авторизація).
- **ID повідомлень.** Свої CALL — з власним префіксом `uniqueId` (напр. `px-…`), щоб не збігалися з ID паркінгу;
  відповіді з таким префіксом паркінгу **не пересилаються**.
- **Одна команда за раз.** В OCPP 1.6 у кожному напрямку — один CALL без відповіді. Якщо паркінг чекає на
  відповідь станції — наша команда стає в чергу (і навпаки: команду паркінгу не пускати, поки висить наша).
- **Нічого не підробляти.** Статуси, транзакції, відповіді — справжні від станції.

## Ризики та відкриті питання

- **Проксі — точка відмови.** Упав проксі — станція офлайн і для паркінгу. Потрібні моніторинг, автоперезапуск;
  варіант аварійного обходу — повернути станції `ConnectionUrl` паркінгу напряму.
- **TLS і авторизація.** Станція підключається до проксі по `wss` (наш сертифікат); проксі до паркінгу —
  з тим самим ID і паролем станції (Basic Auth / сертифікат станції — дізнатися, що використовує Skidata).
- **Переналаштування станції:** `ConnectionUrl` → проксі. Паркінг не повинен цього помітити (ID той самий).
- **Що в `idTag`** при старті з паркувального зчитувача — номер квитка чи внутрішній ID паркінгу. Від цього
  залежить зв'язок «квиток → транзакція».
- **Конфлікт зупинок:** паркінг теж може зупинити сесію — це нормально, просто фіксуємо фактичну енергію.
- **Офлайн між станцією і проксі** — `RemoteStop` не дійде; запобіжники на самій станції — див. CB-009.
- **Згода** власника станцій і перевірка умов договору з постачальником CSMS.

## Що ще дає той самий проксі

- Діагностика без зняття станції з роботи: запис усіх повідомлень з часом сервера, рідкісні збої «раз на тиждень».
- Знімок конфігурації та порівняння до/після (не забути повернути змінені ключі — урок із Supernova).
- Словник кодів помилок вендорів (`vendorErrorCode`, напр. Wallbox `DCF:PMO:…`) і сповіщення про них.
